## 1. Project Overview

**CONFIRMED** (`README.md`): WinOS is an internal team-operations platform
built for **Eagle Eye Digital** (company domain `eagleeyedigital.io`). It
replaces informal Slack-style standup channels and end-of-day check-ins with
a structured workflow:

- Every team member submits a **DSM** (Daily Standup — morning) and a **DSR**
  (Daily Status Review — evening).
- Managers review submissions, set task priorities, track blockers, and
  coordinate support requests.
- Two roles exist: `TEAM_MEMBER` and `MANAGER` (`prisma/schema.prisma`,
  enum `UserRole`).

Beyond the README's stated feature list, the actual directory structure
(`src/features/*`) shows the product has grown well past DSM/DSR into a
broader internal-ops suite: notes, calendar (with Zoho Calendar integration),
user/team management with a granular permission matrix, and an
in-progress Projects module (now DB-backed, see §5). See §5 for the full module
inventory (**CONFIRMED** from directory listing).

Git history (`git log --oneline -20`) shows recent commits like "add user
management module", "fix dark and light mode", "fix bugs and amendments",
"add calendar module" — consistent with an actively developed, iterative
internal tool rather than a stable public product. Remote: single GitHub
repo `github.com/eagleeye-2022/WinOS` (both `origin` and `upstream` point to
the same URL) — **CONFIRMED**.

## 4. Architecture Overview

**CONFIRMED**: This is a **Next.js App Router, server-first application**.
There is no separate backend service — Prisma is called directly from
Server Components, Server Actions (`"use server"` functions in
`src/features/*/actions/*.ts`), and Route Handlers (`src/app/api/**/route.ts`).

Key architectural facts:
- **No `middleware.ts`** exists at the project root or in `src/` (only the
  one bundled inside `node_modules/next-auth`) — **CONFIRMED** via glob
  search. Route protection is therefore done **per-layout/per-page**, not
  via global middleware. `src/app/(dashboard)/layout.tsx` calls `auth()` and
  `redirect(ROUTES.login)` if there's no valid session — this is the single
  gate for the entire `(dashboard)` route group.
- Client-side session freshness is additionally enforced by a
  `<SessionGuard />` component rendered in the dashboard layout
  (`src/components/shared/session-guard.tsx` — not read in full, but
  imported and used at `src/app/(dashboard)/layout.tsx:18,78`).
- Server Actions are the primary write path (forms `action={...}` and
  `useActionState`-style state objects, e.g. `SaveDsmState` in
  `src/features/dsm/actions/save-dsm.ts`). A handful of Route Handlers
  (`src/app/api/**`) exist for cases needing JSON APIs — notably Zoho
  Calendar sync, file uploads, notes sharing feeds, and NextAuth's own
  catch-all route.
- Data layer: Prisma Client generated to a **custom output path**
  (`prisma/generated/prisma`, per `generator client { output = "../generated/prisma" }`
  in `prisma/schema.prisma`), instantiated once in `src/lib/db.ts`
  (singleton pattern is typical for this setup — file itself not fully read
  but is the sole import site referenced everywhere as `@/lib/db`).
- Much application code casts the Prisma client to `any`
  (`const d = db as any;`, seen repeatedly, e.g.
  `src/features/dsm/actions/save-dsm.ts:22`, `src/app/api/zohocalendar/events/route.ts:127,164`)
  — **CONFIRMED**, and called out in inline `eslint-disable` comments. This
  suggests the generated Prisma types and the `db` export's declared type
  don't always line up cleanly (possibly due to the custom output path or a
  wrapper), forcing `any` casts to work around TypeScript friction.

## 6. Frontend Architecture

**CONFIRMED**:
- App Router with two route groups: `(auth)` (login page only,
  `src/app/(auth)/layout.tsx` + `login/page.tsx`) and `(dashboard)` (all
  authenticated app pages, wrapped by `src/app/(dashboard)/layout.tsx`).
- Root layout (`src/app/layout.tsx`) sets up Geist fonts, a `ThemeProvider`
  (from `next-themes`, `src/components/shared/theme-provider`) with
  `attribute="class"`, `defaultTheme="light"`, `enableSystem` — dark/light
  mode is a first-class feature (also evidenced by recent commit "fix dark
  and light mode" and `login-dark.png`/`login-light.png` screenshots at repo
  root).
- Dashboard layout renders: top bar (brand, clock chip, module switcher,
  notification bell, theme toggle, sign-out form posting to
  `logoutAction`), a left sidebar (`AppSidebar`, receives `userRole` and
  `userId` — role-aware navigation), and a `<main>` content area.
- **`AppSidebar`** (`src/components/shared/app-sidebar.tsx`, **CONFIRMED**,
  updated 08-21): a single component whose nav items are recomputed per
  request based on which top-level module the current `pathname` (or a
  `?module=` query param) falls under — People/Projects/Sales/Settings/
  Standup. Each module has its own `navItems` array with real `next/link`
  hrefs (not client-only tab state); `isSubItemActive()` has one bespoke
  active-match rule per label (e.g. `/projects` vs `/projects/my-tasks` are
  matched separately so they don't both light up together). For the
  Projects module specifically, `isManager` (from `userRole === "MANAGER"`)
  gates whether "Users" and "My Tasks" links even render.
- A `RouteDarkScope` component wraps sections conditionally matched against
  `/dsm` — suggests per-route theme overrides exist (**CONFIRMED** usage,
  internals not inspected).
- Components: two-tier system — generic UI primitives in `src/components/ui/`
  (shadcn-style, driven by `components.json` + Radix + CVA), and a very large
  bespoke TipTap rich-text editor toolkit under `src/components/tiptap-*`
  (nodes, extensions, icons, templates, UI buttons) — this is a vendored/
  customized TipTap starter kit, not hand-rolled from scratch (**INFERRED**
  from the completeness and naming conventions matching TipTap's official
  "simple template").
- Data fetching pattern: Server Components call `queries.ts` functions
  directly (e.g. `src/features/dsr/queries.ts` exports typed data-shaping
  functions like `getDsrEntry`-style helpers, inferred from exported types
  `DsrEntryData`, `DsrInsights`) — there's no client-side fetch/query
  library; mutations go through Server Actions bound to `<form action={...}>`
  and presumably `useActionState`/`useFormState` in client components (not
  directly confirmed by file read, but strongly implied by the
  `SaveDsmState`-shaped return types used by `saveDsm`).

## 7. Backend Architecture

**CONFIRMED**:
- "Backend" = Next.js Server Actions + Route Handlers, no standalone Express/
  Nest server.
- Server Actions live in `src/features/<domain>/actions/*.ts`, each file
  starting with `"use server"` and typically: (1) call `auth()` to get the
  session, (2) re-validate the session user against the DB (see §11 for why),
  (3) parse `FormData` via helpers in `src/lib/action-utils.ts`
  (`getStr`, `validateText`), (4) run Prisma writes, often as
  delete-then-recreate "sync" patterns for child collections (tasks,
  blockers, support needs), (5) call `revalidatePath(...)`, and (6) either
  `redirect(...)` on submit or return a state object with `message`/`errors`.
- Route Handlers (`src/app/api/**/route.ts`) follow a simpler
  `NextRequest`/`NextResponse.json()` pattern with manual `auth()` checks and
  try/catch → `NextResponse.json({ error }, { status })` on failure. Sampled
  in full: `src/app/api/zohocalendar/events/route.ts` (GET lists events in a
  date range; POST creates a `CalendarEvent`, resolves attendee users by
  email, fires invite emails via `sendCalendarInviteEmail`
  (`src/lib/email.ts`), and best-effort syncs the event to Zoho Calendar via
  `src/lib/zoho-calendar.ts`, non-fatal on Zoho failure).
- Other Route Handlers cover: NextAuth catch-all (`api/auth/[...nextauth]`),
  a custom Zoho OAuth login/callback pair (`api/auth/zoho/login`,
  `api/auth/zoho/callback` — separate from the app's own OTP login, this is
  specifically for connecting a user's Zoho account to sync calendars),
  `api/captcha`, `api/debug/db-health` (health check), `api/notes/history`,
  `api/notes/shared`, `api/notes/shared-by-me`, `api/uploads` (+ dynamic
  `[filename]` route for serving/retrieving uploads), `api/boards/[boardId]/threads`.

## 8. Database / Data Layer

**CONFIRMED** from `prisma/schema.prisma` (PostgreSQL, Prisma 7 with
`@prisma/adapter-pg`; client generated to `prisma/generated/prisma`):

**Core identity & auth models**: `User` (very large — HR-style fields:
`employeeId`, `employmentType`, `dateOfJoining`, `dateOfConfirmation`,
`dateOfBirth`, `gender`, `maritalStatus`, mobile numbers, parent/guardian
info, `permanentAddress`, `aadharNumber`, `bankAccountNumber`, `ifscCode` —
this is effectively an HRMS employee record, not just an auth identity),
`Account`, `Session`, `VerificationToken` (standard Auth.js/Prisma-adapter
shape), `OtpToken` (custom OTP model with `failedAttempts`, `expiresAt`,
`usedAt`).

**Org structure**: `Team`, `TeamMember`, self-referential `User.reportingTo`
/ `User.secondaryReportingTo` (dual-manager hierarchy support).

**DSM domain**: `StandupEntry` (unique per `[userId, date]`, status enum
`DRAFT|SUBMITTED|PENDING_REVIEW|REVIEWED|MISSED`), `StandupTask` (kind
`YESTERDAY|TODAY`), `StandupBlocker` (+ `StandupBlockerMention` for
multi-user @mentions, `BlockerComment`), `StandupSupportNeed` (+
`StandupSupportNeedMention`, `SupportNeedComment`, optional link to a
`CalendarEvent`), `DsmWorkspaceNote` + `DsmActionItem` (one-per-user
scratch workspace, `@unique ownerId`).

**DSR domain**: `DsrEntry` (unique per `[userId, date]`, status mirrors
StandupEntry's enum, `sentiment` enum `BREAKTHROUGH|BREAKDOWN`,
`completionPercent`), with child collections `DsrPlannedTask`,
`DsrAdditionalWork`, `DsrResolvedBlocker`, `DsrFollowUpDone`,
`DsrLearningItem`, `DsrTimelineEvent` — all `onDelete: Cascade` from the
parent entry.

**Notes/Boards domain**: `Notebook`, `Tag`, `NoteTag` (join), `Note`,
`ChecklistItem` — personal notes. Separately, a **Board/Thread/BoardNote**
system (`Board`, `BoardShare`, `Thread`, `ThreadShare`, `BoardNote`,
`BoardNoteShare`, `BoardNoteChecklistItem`) — a Trello/Miro-like shared
sticky-note board with per-board/thread/note sharing and edit permissions.
`Board.type` distinguishes `"DSM" | "NORMAL"` boards (string field, not an
enum) — implying DSM has (or had) an alternate board-based UI.

**Permissions**: `PermissionModule` → `PermissionAction` → `PermissionRule`
(keyed by `ProfileRole` enum: `EMPLOYEE|MANAGER|CONTRACTOR|CLIENT|GUEST|
DEVELOPER|SUPPORT`), with `PermissionScope` enum (`NONE|OWNED|ALL|BOTH`) and
boolean/scope control types — this is a **fully data-driven RBAC matrix**,
separate from the simpler `User.role` (`TEAM_MEMBER|MANAGER`) used for
route/session gating. The matrix is exposed in the UI via
`src/features/users/components/permission-matrix.tsx` and
`permission-access-workspace.tsx`, backed by `src/features/users/actions/
permission-actions.ts`. `src/features/users/permission-config.ts` defines
UI-side profile/role metadata (`PROFILE_CONFIG`) matching the Prisma enum
values.

**HR documents**: `UserDocument`, `IcaDocument`, `RoleTaskDocument`,
`IcebergProfile` (coaching notes), `CompetencyAttribute` (skill/knowledge/
trait tracking, category enum) — these back the `people/ica` pages.

**Calendar**: `ZohoAccount` (per-user OAuth token storage: access/refresh
token, expiry, domains, primary calendar UID), `CalendarEvent`,
`CalendarEventAttendee` (status/role, unique on `[eventId, email]`, nullable
`userId` for external attendees).

**Notifications**: `Notification` (type enum `DSM_REMINDER|CALENDAR_INVITE`,
sender/receiver relations).

**Projects** (**Updated 08-21, CONFIRMED**): `Project`, `ProjectPhase`,
`ProjectTask`, `ProjectSubtask`, `ProjectTaskRemark`, `ProjectTaskActivity`,
`ProjectTimeLog`, plus `ProjectTaskList`, `ProjectMember` (join table for
project↔user assignment). `Project.ownerId`/`ProjectTask.ownerId`/`.authorId`
now have real relations to `User`, and the placeholder string defaults have
been genericized (`ownerName String? @default("Unassigned")`, `startDate
String? @default("--")`) — the earlier hardcoded person-name/future-date
defaults are gone. The module is live-DB-backed end to end (see §5); the
`src/features/projects/data/mock-*.ts` files are unused leftovers.

Migrations: only one migration folder present, `prisma/migrations/0_init/`
(**CONFIRMED** via `find`), meaning schema evolution has mostly happened via
`db push` in dev (per `README.md`'s dev instructions using `prisma db push`
rather than `migrate dev`) with `migrate deploy` only applied in the Amplify

## 9. API Structure

**CONFIRMED** — two API surfaces:

1. **Server Actions** (primary): not URL-addressable; imported directly into
   Server/Client Components and bound to forms. Naming convention:
   verb-first files (`save-dsm.ts`, `create-blocker.ts`, `mark-resolved.ts`,
   `send-reminder.ts`, `delete-thread.ts`, etc.), one exported async
   function per file, most returning a `{ message?, errors? }` state shape
   for `useActionState`.
2. **Route Handlers** under `src/app/api/`, REST-ish JSON endpoints:
   - `api/auth/[...nextauth]` — Auth.js catch-all
   - `api/auth/zoho/login`, `api/auth/zoho/callback` — Zoho OAuth handshake
     for connecting a user's Zoho account (distinct from the app's own login)
   - `api/zohocalendar/{calendars,disconnect,events,events/[id],status}` —
     Zoho Calendar CRUD/status proxy
   - `api/boards/[boardId]/threads` — board thread listing/creation
   - `api/notes/{history,shared,shared-by-me}` — notes feed endpoints
   - `api/uploads`, `api/uploads/[filename]` — file upload/serving
   - `api/captcha` — captcha generation/verification (`src/lib/captcha.ts`)
   - `api/debug/db-health` — DB health check endpoint

Convention observed in every sampled handler: `auth()` check first →
`401` if missing, `request.json()` / `request.nextUrl.searchParams` for
input, manual field validation with early `400` returns, try/catch around
the DB/external-API work with `console.error` + `500` JSON error response
carrying `error.message` when available.

## 10. Authentication & Authorization

**CONFIRMED**, `src/lib/auth.ts`:

- **Passwordless OTP login** via Auth.js v5's `Credentials` provider —
  a single provider taking `{ email, otp }`.
- **Domain restriction**: only `@eagleeyedigital.io` emails are accepted,
  enforced server-side in `authorize()` (line 37): `email.endsWith(
  "@eagleeyedigital.io")`.
- **Auto-provisioning**: if no `User` row exists for a valid email + OTP,
  one is created on the fly, with role assigned from a hardcoded
  `MANAGER_EMAILS` allow-list (4 emails, `src/lib/auth.ts:9-14`) — anyone
  else auto-provisioned gets `TEAM_MEMBER`. This means **new employees are
  not manually pre-created**; they're created lazily on first successful
  OTP login (despite `README.md` saying users must have a "pre-provisioned"
  account — the code contradicts this claim; the code allows auto-creation).
- **OTP verification**: `verifyAndConsumeOtp(email, otp)` from
  `src/lib/otp.ts` (not fully read, but confirmed as the single-use,
  TOCTOU-safe gate per the inline comment at `auth.ts:48-49`); OTP model
  (`OtpToken`) tracks `failedAttempts`, `expiresAt`, `usedAt`. Structured
  logging of OTP lifecycle events (never the code itself) goes through
  `src/lib/logger.ts`'s `logOtp()`.
- **Inactive users blocked**: both at `authorize()` time (line 44-46) and
  again in the `session()` callback (line 103), which re-queries the DB on
  every session read to check `isActive` and current `role` — if the user
  was deactivated after login, their session is invalidated (`user:
  undefined`) without needing to wait for JWT expiry.
- **JWT session strategy** (`session: { strategy: "jwt" }`), `trustHost:
  true` (required behind AWS Amplify's reverse proxy per inline comment).
  Custom sign-in page at `/login`.
- **Route protection**: no middleware; enforced in
  `src/app/(dashboard)/layout.tsx` via `auth()` + `redirect` (§4), and
  supplemented client-side by `<SessionGuard />`.
- **Role-based logic**: `User.role` (`TEAM_MEMBER | MANAGER`) drives simple
  UI/route branching (68 files reference `role === "MANAGER"` or
  `role !== "MANAGER"` per grep count) — e.g. manager-only pages like
  `dsm/all`, `dsr/manage`, `dsm/member/[userId]`, `notes/member/[userId]`.
  A second, much richer **data-driven permission system**
  (`PermissionModule`/`PermissionAction`/`PermissionRule`, §8) exists in
  parallel for fine-grained module/action/scope control, surfaced at
  `settings/profile-access` — the exact relationship/precedence between
  the simple `role` checks scattered through the app and this permission
  matrix was **not fully traced (UNCLEAR)**; they may be partially
  overlapping systems (the matrix looks newer, per the recent "add user
  management module" commit).
- **Zoho OAuth** is a *separate* per-user integration (connecting a
  personal Zoho Calendar account), unrelated to WinOS's own login — tokens
  stored in `ZohoAccount`, refreshed via `getValidZohoAccessToken()` in
  `src/lib/zoho-calendar.ts`.
- Every Server Action re-validates the session user exists in the DB
  before writing (see `save-dsm.ts:24-43` and the extensive comment
  explaining why: JWT cookies aren't re-validated per-request by Auth.js
  itself, so after a local DB reset a stale CUID in the cookie would
  otherwise cause FK-constraint failures on every write). This is a
  recurring defensive pattern worth knowing about when debugging "session
  no longer valid" errors during local dev.

## 11. Important Business Logic

**CONFIRMED**, primarily from `src/features/dsm/actions/save-dsm.ts`
(read in full) and schema-level status enums:

- **DSM submission lifecycle**: `StandupEntry.status` moves
  `DRAFT → SUBMITTED → PENDING_REVIEW → REVIEWED` (or `MISSED` presumably
  set by a scheduled/cron process not found in the explored code —
  **UNCLEAR** how `MISSED` gets set, no cron/scheduled job files were
  found in this exploration).
- **Draft vs. submit**: the same `saveDsm` action handles both, keyed off a
  hidden `action` form field (`"draft"` vs `"submit"`). Validation
  (at least one task, non-empty learning text) only runs on submit.
- **Edit-after-submit semantics**: if a member edits an entry that was
  already `SUBMITTED`/`PENDING_REVIEW`, saving again keeps it as
  `PENDING_REVIEW` rather than reverting to `DRAFT` — explicitly called out
  in a comment (`save-dsm.ts:104-107`) as intentional, since a `DRAFT`
  status would hide the entry from manager review.
- **Immutability after review**: once `status === "REVIEWED"`, the member
  can no longer modify the entry (`save-dsm.ts:100-102`).
- **Child-collection sync pattern**: tasks/blockers/support-needs are
  fully deleted and recreated on every save rather than diffed
  (`deleteMany` + `createMany`/loop of `create`) — simpler but means IDs of
  child rows change on every edit (relevant if any UI holds onto blocker/
  support-need IDs across a save).
- **@Mentions**: blockers and support-needs support mentioning multiple
  users — stored redundantly both as a legacy denormalized comma-joined
  string (`mentionedUserId` for the first ID, `mentionedUserIds` as a CSV)
  *and* as a proper join table (`StandupBlockerMention`,
  `StandupSupportNeedMention`) — **CONFIRMED** dual storage, likely a
  migration-in-progress from the old single/CSV scheme to a real relational
  one (the code writes both, `save-dsm.ts:155-163`).
  A recent commit "fix: mention error" corroborates this area having had
  bugs.
  Note: the action code doesn't parse `d.standupSupportNeedMention` for a
  case where `resolved` is set on support needs from DSM — support needs
  created via `saveDsm` default `resolved: false`, distinct from resolution
  actions in `support-needed/actions/mark-resolved.ts`.
- **Support-need ↔ Calendar linking**: `StandupSupportNeed.eventId`
  optionally links a support request to a `CalendarEvent`
  (`support-needed/actions/link-support-event.ts`) — i.e. a support request
  can be resolved by scheduling a meeting.
- **DSR mirrors DSM structurally**: same status enum, similar
  draft/submit/review lifecycle (inferred from schema symmetry; only
  `queries.ts` types were read for DSR, not the save action itself, so the
  exact save-time business rules for DSR were **not directly confirmed** —
  reasonable to assume parity with `save-dsm.ts` given the shared
  `DsrStatus` enum values).
- **Sentiment tracking**: DSR entries capture `BREAKTHROUGH`/`BREAKDOWN`
  sentiment plus `resultOfDay`/`reflection` free text and `completionPercent`
  — used to compute `DsrInsights` (streaks, weekly trend, "insight quote") per
  `src/features/dsr/queries.ts` type definitions.

## 18. Important Data Flows

### Flow: Submitting a DSM (Daily Standup)

**CONFIRMED**, traced through `src/features/dsm/actions/save-dsm.ts` and
`prisma/schema.prisma`:

1. **Frontend**: A team member fills out the standup form (rendered by
   `src/features/dsm/components/submit-dsm-form.tsx`, not read in full but
   the sole plausible entry point given the feature's component naming) on
   `/dsm` (or `/dsm/my` for managers). The form's `action` prop is bound to
   the `saveDsm` Server Action; fields include `action` (`"draft"|"submit"`),
   `date`, `learningText`/`learningItemText[]`, repeated `taskText[]` +
   `taskPriority[]`, repeated `blockerText[]` + `blockerPriority[]` +
   `blockerUserId[]` (comma-joined mention IDs), and the equivalent
   `supportText[]`/`supportUserId[]` fields.
2. **Server Action invocation**: Next.js calls `saveDsm(prevState, formData)`
   server-side (no explicit HTTP boundary from the developer's perspective —
   Next.js handles the RPC).
3. **Auth check**: `await auth()` — if no `session.user.id`, immediately
   return `{ message: "Unauthorized" }`, no DB access.
4. **Session/DB consistency guard**: re-queries `User` by ID or email to
   guard against a stale JWT pointing at a deleted user (common after local
   DB resets) — returns a friendly "session no longer valid" message rather
   than crashing on a foreign-key violation.
5. **Parse & branch**: extracts all form fields; if `action === "submit"`,
   validates at least one task exists and learning text is non-empty,
   returning field-level errors otherwise (form presumably re-renders with
   these errors via `useActionState`).
6. **Status-transition guard**: fetches the existing `StandupEntry` for
   `[userId, date]`; blocks any write if it's already `REVIEWED`; if it was
   previously `SUBMITTED`/`PENDING_REVIEW`, forces the new status to stay
   `PENDING_REVIEW` (never regress to `DRAFT`) so it remains visible to
   managers.
7. **DB writes** (all inside a sequence of Prisma calls, not an explicit
   `$transaction` — **CONFIRMED** no `db.$transaction` wrapper was seen in
   this action, meaning a mid-sequence failure could leave partially-synced
   child records, a potential consistency risk flagged in §19):
   - `standupEntry.upsert` on `[userId, date]`.
   - `standupTask.deleteMany` (kind=TODAY) then `createMany` with the new
     task list.
   - `standupBlocker.deleteMany` (all for this entry) then per-blocker
     `create`, plus `standupBlockerMention.createMany` for any @mentioned
     users beyond the first.
   - Same delete/recreate pattern for `standupSupportNeed` +
     `standupSupportNeedMention`.
8. **Error handling**: Prisma errors are caught; a `P2003` (FK violation)
   maps to the "session no longer valid" message; anything else maps to a
   generic "Failed to save" message. Errors are logged via `console.error`
   with the Prisma error code/meta.
9. **Response**: on success, `revalidatePath(selfPath)` invalidates the
   Next.js cache for `/dsm` or `/dsm/my` (role-dependent); if this was a
   `"submit"` action, `redirect()`s to `${selfPath}?submitted=1` (client
   sees a fresh navigation with a submitted-confirmation query flag);
   otherwise (draft save) returns `{ message: "saved" }` for the form to
   display inline.
10. **Downstream read path** (manager review): a manager visiting `/dsm/all`
    or `/dsm/member/[userId]` reads via `src/features/dsm/manager/
    queries.ts` (not read in full, but the counterpart read path to the
    write flow above) — presumably filters `StandupEntry` by status
    `SUBMITTED`/`PENDING_REVIEW` for team members reporting to them,
    given the `User.reportingTo`/`secondaryReportingTo` hierarchy in the
    schema (**INFERRED** — the manager query internals weren't directly
    read).

### Flow: Creating a Calendar Event (secondary flow, fully read)

Frontend (`event-dialog.tsx`, POSTs JSON) → `POST /api/zohocalendar/events`
→ `auth()` check → validate title/start/end → resolve invitee emails to
existing `User` rows → `db.calendarEvent.create` with nested `attendees`
create (organizer + matched users + unmatched external emails) → fire
`sendCalendarInviteEmail` per non-organizer attendee (async, errors logged
but non-fatal) → best-effort `getValidZohoAccessToken` + `createZohoEvent`
sync (also non-fatal on failure) → `revalidatePath("/calendar")` and
`/zohocalendar` → JSON response with the created event and Zoho sync status.

## 19. Potential Areas of Complexity

**CONFIRMED/INFERRED risk areas surfaced during exploration**:

1. **No explicit DB transactions in multi-step writes**: `saveDsm` (and
   likely its DSR/blocker/support-need counterparts, given the shared
   pattern) performs several sequential Prisma calls (upsert entry, delete+
   recreate three child collections) without wrapping them in
   `db.$transaction([...])`. A failure partway through (e.g. after tasks are
   deleted but before they're recreated) could leave the entry in an
   inconsistent state. **CONFIRMED** absence of `$transaction` in the one
   file read in full; not verified across all similar actions.
2. **Dual mention storage**: blockers/support-needs store mentions both as
   a legacy `mentionedUserId`/CSV `mentionedUserIds` string pair *and* as a
   proper join table. Any code reading mentions must know to check both, and
   they could drift out of sync if one write path updates one but not the
   other. Recent commit history ("fix: metion error") suggests this has
   already caused bugs.
2b. **Extensive `as any` casting of the Prisma client** across actions and
   route handlers defeats TypeScript's ability to catch schema-mismatch
   bugs at compile time — a latent source of runtime errors that the type
   system would otherwise prevent.
3. **Two parallel authorization systems**: simple `User.role` checks
   (`TEAM_MEMBER`/`MANAGER`, scattered across ~68 files) coexist with a
   fully data-driven `PermissionModule/Action/Rule` matrix keyed on a
   different, richer `ProfileRole` enum. How (or whether) these two systems
   are reconciled at runtime was not established in this exploration —
   worth clarifying before extending permission logic.
4. **(Resolved 08-21)** Projects module is now fully DB-backed — see §5/§8.
   The old `src/features/projects/data/mock-*.ts` files are unused dead code
   (nothing imports them); safe to delete but harmless to leave as-is.
5. **`auth.ts` auto-provisions users on first OTP login** using a hardcoded
   in-code `MANAGER_EMAILS` set — adding a new manager requires a code
   change/deploy, not a DB/admin-panel update, unless the newer permission
   matrix supersedes this for authorization purposes (unclear per #3).
6. **Local `.env` appears to point at what looks like a live/shared Neon
   database** rather than a local Docker instance described in the README
   workflow — risk of local development scripts (`db:seed`, test runs)
   accidentally mutating shared data. Worth confirming with the team.
7. **e2e/verification scripts are not part of CI** — the screenshot-
   producing scripts in `scripts/` (and the two screenshot directories) are
   apparently run manually or by an agent, not gated in `ci.yml`, so
   regressions they'd catch aren't automatically enforced.
8. **Next.js 16 is very new** — `AGENTS.md` explicitly warns that APIs may
   differ from an LLM's training data; this is a standing instruction to
   consult `node_modules/next/dist/docs/` before writing new code against
   the framework.
